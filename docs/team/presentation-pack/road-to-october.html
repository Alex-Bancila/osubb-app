Method

How to work one issue, start to finish

Every issue below follows the same loop. Once you've done it twice it takes zero thought — that's the point: all creativity goes into the task, none into the process.

1 · Pickan open issue whose "Depends on" is done
→
2 · Branchgit checkout -b feat/…
→
3 · Buildfollow the issue's How steps
→
4 · Verifydb reset + test db green locally
→
5 · PRpush, open PR "Closes #n"
→
6 · MergeCI green → review → merge → staging updates itself

The loop. Steps 4 and 6 are the two safety gates — never skip them.

The commands, concretely (backend issue shown; frontend swaps step 4 for npm run build + the app in the browser):

# 1–2
git checkout main && git pull
git checkout -b feat/1.5a-events

# 3 — for a schema issue:
npx supabase migration new events_attendance
#    …write SQL in the new file under supabase/migrations/…
#    …add tests in supabase/tests/…

# 4 — the two green lights:
npx supabase db reset     # every migration applies from scratch
npx supabase test db      # all pgTAP suites pass

# 5
git add -A && git commit -m "feat(db): events + attendance (1.5a)"
git push -u origin feat/1.5a-events
gh pr create --title "1.5a Events + attendance" --body "Closes #43"
Definition of done

An issue is done when: the migration applies on db reset · its pgTAP tests pass (and would fail if the feature were removed) · CI is green on the PR · the acceptance-criteria boxes in the issue are checked · the PR says Closes #n so the issue closes itself on merge.

House rules that every issue already assumes: new tables get enable row level security in the migration that creates them; new views get with (security_invoker = on); functions used by policies or triggers get set search_path = '' and fully-qualified names; reference data goes in migrations, demo data in seed.sql; secrets never in git.

Strategy

Why this order and not another

The sequence below isn't taste — it follows three dependency rules:

  • Tables before policies before screens. A policy can't protect a table that doesn't exist; a screen can't render data it isn't allowed to read. So every feature travels: schema → RLS → UI.
  • The invite flow before any real login. ADR-0003 means there is no other way to get a user. Every end-to-end test of auth, and the demo logins' magic-link path, sit behind it.
  • Demo data before the first screen. A screen built against an empty database looks done and lies. Seeding one login per role first means every screen PR can be reviewed by actually clicking through it as each role.

And one scheduling rule: anything only a human can do (create accounts, click dashboards, talk to BC) is pulled early, because human steps have calendar latency — the code can wait an hour, a BC meeting can't happen tonight.

Remaining data tables

Why this exists: four v1 features (calendar, announcements, notifications, AG sheets) still have no tables. These five issues finish the entire v1 schema. They don't depend on each other — perfect parallel work, and perfect first issues for a volunteer because the spec literally contains the SQL to adapt.

#431.5a Events + attendance tablesdone

What: events (title, type, scope, dept/team, start/end, location, capacity) and event_attendance (who RSVPed what). How: new migration, DDL from spec §3.4, RLS on both, indexes on dept/team/starts_at. Why: the calendar and its whole policy tree (#62–63) stand on these two tables. The composite primary key (event, member) is what makes double-RSVP physically impossible — a nice example of letting the database enforce a business rule.

Depends: nothing · Spec §3.4
#441.5b Announcements + reads tablesdone

What: announcements (title, body, priority, pinned, optional Google-Forms link) and announcement_reads (read receipts). Why: the org megaphone — and form_label is the whole v1 "forms engine": a link to Google Forms, native forms deferred to Phase 4. Read receipts power both the unread badge and the "critical pop-up until read" behavior.

Depends: nothing · Spec §3.4
#451.6a Notifications tabledone

What: notifications — one row per (recipient × event): kind, title, body, read flag, link. Why: in-app notifications are v1; Phase-2 push will deliver these same rows to phones, so getting the shape right now means push later is delivery-only.

Depends: nothing · Spec §3.4
#461.6b Suppression seed + push tokensdone

What: notif_suppression seeded with six rows — bc AND bce × task/event/deadline — plus push_tokens for future devices. Why: this seed is the resolution of conflict C2 from the plan analysis: leadership stops drowning in broadcast noise. Careful: the spec's original insert says bc-only; Revision 3 supersedes it — seed both roles.

Depends: nothing · Spec §3.4 + Revision 3 §9.2
#471.7a ag_eligibility view~30 min

What: a view listing active members with their totals and eligible = points ≥ 300. Why: the AG attendance sheet becomes a live query instead of a maintained spreadsheet — it can never be out of date. Remember the house rule: security_invoker = on.

Depends: nothing · Spec §3.5
#481.7b ag_quorum_top25 view~45 min

What: of the eligible, the top 25% by points keep voting rights (keeps_vote), via a percent_rank() window function. Why: statute rule from the mockup. It's also a gentle introduction to window functions for whoever takes it — the test fixture (4 members, exactly one keeps the vote) teaches the concept.

Depends: #47 · Spec §3.5
#61.8 joined_at + sanction note~30 min

What: add profiles.joined_at (backfilled from joined_year) and points_ledger.note. Why: the semester promotion rule (#51) computes from a real date, and the mandate says sanctions carry a written reason — the reason belongs next to the points, not in someone's chat history.

Depends: nothing · Revision 3 §9.3
Section B · Sprint 1 · sequential chain

The invite flow — how people get in

Why this exists: ADR-0003 says accounts are created only by invitation. Right now that flow doesn't exist, which means no real person can log in at all. This chain builds it in three strictly-ordered steps, smallest possible pieces: pure database function → web function → proof + manual.

#562.3a provision_profile() RPCdone

What: one SQL function that, given a user id + role + departments + teams, creates the profiles row and all membership rows atomically (all or nothing). Callable by the server only. Why: both single invites and the CSV import must share one provisioning path — one code path means a member can never be half-created, and there's one set of bugs to fix, not two. How: SECURITY DEFINER migration, revoke execute from clients, pgTAP proves atomicity (a bad dept id rolls back everything) and that clients get 42501.

Depends: nothing · Spec §5.1
#572.3b Edge Function: invite-memberdone

What: a small server function (Deno/TypeScript — first one in the repo): checks the caller's JWT is level ≥ 6, calls Supabase's admin API to send the magic-link invite, then calls #56 to provision. Why: this is the button BC will press. Edge Functions are where logic goes when it needs the service key — which clients must never hold. How: npx supabase functions new invite-member, read caller claims, auth.admin.inviteUserByEmail, clear errors (duplicate → 409).

Depends: #56 · Spec §5.1
#582.3c Invite e2e check + runbookdone

What: invite a test member locally, open the magic link in Mailpit (the local fake inbox at 127.0.0.1:54324), log in, confirm the token carries role/level claims; write docs/backend/inviting.md — the BC manual. Why: "it probably works" is not a launch plan; this issue converts the flow from code into a demonstrated capability plus instructions a non-technical BC member can follow.

Depends: #57
#532.1a Verify + document auth configdone

What: a written table of every auth setting (signup off, confirmations on, hook enabled) with the reason for each, cross-checked against ADR-0003. Why: configuration is the easiest thing to break silently six months later — the doc is the tripwire.

Depends: nothing
#542.1b Staging dashboard checklist🧍 ~20 min

What (you, in the browser): enable the JWT hook on staging (Authentication → Hooks → Customize Access Token → public.custom_access_token_hook) and set the Site URL once the frontend exists. Why: hosted projects don't read config.toml — without this, staging logins would produce tokens with no role stamps and every screen would look empty.

Depends: #58 (needs an invited user to verify with)
Section C · Sprint 1 · after their tables exist

Remaining permissions (RLS)

Why this exists: the database is deny-by-default since PR #41 — tasks and points got their policies in PR #42, but profiles, teams, calendar, announcements and notifications are still fully locked. Each issue here opens exactly one slice of the spec's §4.3 matrix and ships the per-role tests that prove the fence. Pattern to copy every time: PR #42's migration + test file.

#593.2a Profiles read + contact gatingdone

What: everyone reads names/roles (the app is unusable otherwise); email + phone visible only to yourself or level ≥ 5. Why: personal data of ~200 students — GDPR-mindedness is not optional for an NGO. How: the subtlety is that RLS filters rows, not columns, so contact fields need column-level gating (a directory view without the columns + a gated path with them) — the issue describes the pattern; it's the trickiest of the three.

Depends: nothing · Spec §4.3
#603.2b Self-edit + role-change guard~60 min

What: you may edit your own contact info; nobody below level 6 can change role or status — including their own. Why: self-service without self-promotion. How: UPDATE policy + a small BEFORE UPDATE trigger that raises if a protected column changes under level 6 (RLS alone can't compare old vs new values — the trigger can).

Depends: #59 · Spec §4.3
#613.2c Teams + reference-data policiesdone

What: read-for-everyone on the vocabulary tables (roles, departments, scoring guides, capabilities, teams, memberships); team management at level ≥ 5. Why: currently even the list of departments is invisible to a logged-in member — screens can't render a dept chip without this.

Depends: nothing · Spec §4.3
#623.4a Event visibility + writedone

What: THE calendar rule: level ≥ 4 sees all; org-scope and call/recrutare types are for everyone; dept events for dept members; team events for team members — plus recruits when the team is a recruit team. Writes at level ≥ 4. Why: this one policy is the mockup's eventVisible() function relocated to the only place it can't be bypassed. How: the spec §4.4 sketch is 90% copy-paste; the tests (one event per branch × three personas) are the real work.

Depends: #43 · Spec §4.4
#633.4b RSVP policies~45 min

What: RSVP is self-only, and only to events you can see (the policy queries events, whose own RLS applies transitively — the same elegant trick task_assignees uses). Why: the one thing every member writes weekly must be forge-proof.

Depends: #62
#643.5a Announcements policiesdone

What: everyone reads; level ≥ 4 posts; read-receipts are self-only. The simplest policy issue — a good first RLS task for a volunteer.

Depends: #44 · Spec §4.3
#653.5b Notifications policies (suppression!)~50 min

What: you read only your own notifications, minus the kinds your role suppresses (a lookup into #46's table); clients can't insert at all. Why: conflict C2 enforced at the database — a bug in any screen can never re-flood BC with task noise. The test that matters: a bc persona does NOT see a task-kind row addressed to them; a voluntar does.

Depends: #45, #46 · Spec §4.4
#663.5c Interne gating + push tokens~45 min

What: the AG views answer only for level ≥ 6 (seeInterne); device tokens are strictly personal. Why: who keeps voting rights is sensitive leadership information.

Depends: #47, #48, #46 · Spec §4.3
#676.1u Umbrella: per-role suite completefinal sweep ~45 min

What: a tracking issue — every policy issue above ships its own tests; when the last one merges, one final sweep adds any missing cross-role case from the original 6.1 acceptance list, then this closes. Why: so "the permission model is fully tested" is a checkbox someone actually ticks, not an assumption.
