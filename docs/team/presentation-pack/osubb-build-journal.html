Part 1

What we're building

The OSUBB app is the internal tool your mandate promised: one place where members see their tasks, earn points for graded work, follow the calendar and RSVP to events, read announcements, and get notifications — with BC managing roles, awards, and sanctions from the same place.

The delivery calendar (written down in docs/roadmap.md) has three dates that shape everything:

  • ~September 15 — a full demo of the core app for BC;
  • October 1 — live for BC/BCE (~20 leadership members);
  • November — org-wide, timed with autumn recruitment.

We deliberately cut version 1 down to the core (tasks/points/requests, accounts & roles, dashboard, calendar + RSVP, announcements, in-app notifications). Calendar sync, QR check-in, the recruitment pipeline, a native forms engine, contracts and push notifications are all planned, but pushed to later phases — because a small team hits October 1 only if version 1 is small.

Part 2

The starting point

Before this build sprint, the project already had good bones — but they existed only on your laptop:

  • a detailed architecture specification (the technical blueprint: database tables, permission rules, screen-by-screen data needs);
  • a clickable HTML mockup (the one you presented to BC);
  • three ADRs — Architecture Decision Records;
  • one database migration with the core tables;
  • the two mandate PDFs (the requirements source).
In plain words — ADR

An Architecture Decision Record is a one-page document that says: "we decided X, here's the context, here's what we considered, here's why X won." Six months from now, when someone asks "why is sign-up disabled?!", the answer is a file in the repo, not a memory in someone's head. ADRs are how a team avoids re-arguing settled questions.

The three existing decisions: ADR-0001 — use Supabase (a hosted PostgreSQL database with authentication built in) with Row-Level Security as the permission engine; ADR-0002 — build the frontend with React + Ionic, wrapped by Capacitor for phone apps later; ADR-0003 — access is invite-only (more on that in Part 7).

What was missing was everything that turns a design into a project: no git history, no GitHub repository, no task backlog anyone could pick up, no automated checks, and a handful of open questions and contradictions inside the documents themselves.

Part 3

Fixing the plan before writing code

The first real work wasn't code — it was reading everything (spec, mockup, both mandate PDFs) side by side and listing where they disagreed. That surfaced 5 contradictions and ~19 mandate features the technical spec had no answer for. Building on top of contradictions means rebuilding later, so each one got a written resolution first. The important ones:

  • Promotions. The spec said "manual, with suggestions"; the mandate said "automatic and gamified". You decided the final policy: Recrut → Voluntar happens automatically after one semester, Voluntar → Membru Activ automatically at a points threshold, and everything above (Drept de Vot, Responsabil, BCE, BC) stays strictly manual. Recorded as ADR-0004, with thresholds stored as configuration so BC can change them without a programmer.
  • Account creation. Three documents described three different mechanisms (temporary passwords, random passwords, magic links). Resolution: magic links everywhere — nobody ever generates or distributes a password.
  • Notification quiet-mode for leadership. Documents disagreed on whether only BC or also BCE get reduced notifications. Resolution: both BC and BCE, but notifications about their own tasks always arrive.
  • Rollout (ADR-0005): web app first, BC/BCE first, org-wide at recruitment, phone-store apps later. Data retention (ADR-0006): alumni keep their history.

The 19 gaps (projects, task templates, QR check-in, AGO reports, birthday tracking, and so on) were each assigned a phase, so nothing from the mandate is forgotten — it's all in a traceability table appended to the spec ("Revision 3"). The two mandate PDFs were also converted to markdown inside the repo (docs/org/), so the requirements live next to the code they justify.

Finally, two standing documents came out of this: docs/roadmap.md (the sprint calendar, success metrics, and a log of deliberately-deferred decisions) and docs/team/team-plan.md (roles for your 1–3 volunteers, training sessions, review rules). And the whole plan was broken into 37 GitHub issues across 11 epics — each one a self-contained task with acceptance criteria, so any team member (or an AI agent) can pick one up without extra context.

Part 4

The machinery: repo, reviews, robots

Everything now lives at github.com/Alex-Bancila/osubb-app (private). Three habits were set up around it, and they're worth understanding because they're how professional teams work:

1. Version control (git)

Every change is a commit — a snapshot with a description of what changed and why. The full history is preserved forever: anything can be inspected, compared, or undone. Nothing important exists "only on someone's laptop" anymore.

2. Pull requests — one issue, one review

Work never lands directly on the main copy of the code. It goes on a side branch, then a pull request (PR) proposes merging it. The PR shows exactly what would change, line by line. You review and press merge. That's the quality gate — and it's why every feature below arrived as a numbered PR you merged yourself.

3. CI — a robot that distrusts everyone equally

In plain words — CI

Continuous Integration is a script that runs automatically on every pull request, on GitHub's servers. Ours builds a fresh, empty database from scratch, applies every migration, and runs the entire test suite. If anything fails, the PR gets a red ✗ and shouldn't be merged. It takes 3–5 minutes and it never gets tired, skips a step, or says "it worked on my machine".

The same robot has a second job. When you merge to main, it automatically applies any new migrations to the staging server:

→

→

→
Staging updatesautomatically, seconds later

The pipeline every change travels. Nobody deploys by hand; nobody can forget a step.

Docker — what actually runs "local"

In plain words — Docker

A container is a small, isolated, disposable copy of a machine, pre-loaded with one piece of software and everything it needs to run — no "works on my machine" arguments about library versions, because the library is the container. Docker is the tool that downloads, starts and stops containers.

When you run npx supabase start, Docker starts about nine containers at once — Postgres itself, the Auth server (GoTrue), the API gateway (PostgREST/Kong), Studio, Mailpit, and a few more — already wired to talk to each other exactly as they will on the hosted project. That's why "local" isn't a simplified stand-in for Supabase; it is Supabase, just running on your machine instead of theirs. And because containers are throwaway, npx supabase stop or a bad experiment costs nothing — delete the containers, run start again, you're back to a clean slate in under a minute.

Three environments

Local — the full backend running in Docker on your machine, as above; safe to break, rebuilt in one command. Staging — the hosted Supabase project you created; a shared test server that always mirrors main's schema automatically, and its demo data on request (more on that split in the update below). Production — doesn't exist yet, on purpose; it gets created in Sprint 3, right before real data, on the paid plan with backups and a spending cap.

Secrets

Passwords, tokens and keys never go into git — git history is forever, so a leaked secret in a commit stays leaked. They live in two places only: your Bitwarden vault (for humans) and GitHub Actions secrets (for the robot). That's why the CI can deploy to staging without the credentials appearing anywhere in the code.

Part 5

The database foundation

In plain words — migration

A migration is a numbered SQL file that changes the database's shape: "create this table, add that column." The database is never edited by hand — you write a migration, and every environment (your laptop, a teammate's laptop, staging, production) replays the same files in the same order and ends up identical. The database's structure becomes code: reviewable, versioned, reproducible. We have six migrations so far.

The first migration created the vocabulary of the organization as tables:

  • roles — the 8 roles, each with a numeric level. This number is the heart of the whole permission model: instead of writing rules per-role, rules say "level ≥ 4 may grade tasks", and adding a future role never breaks them.
  • departments — the five real departments plus IT coordination, with their brand colors: EDU, Imagine & PR, Tineret, Financiar, HR.
  • profiles — one row per member (name, email, role, status), linked to their login account.
  • teams + membership tables — who belongs to which department and team.
  • rating_guide and difficulty_guide — the official scoring guide, as data BC can amend, not as numbers buried in code.

One convention matters here: reference data (roles, departments, the scoring guide) is inserted inside migrations, so it reaches staging and production automatically. Demo data (fake members and tasks for testing) goes in a separate seed file that only runs locally. Production will never accidentally contain "Ana Test".

The second migration (PR #38) added the work itself: tasks (title, department/team, difficulty 1–5, rating 1–5 once graded, deadline, status), task_assignees (who's on each task — several people can share one), and task_requests (a member proposing "give me points for X" or "create this task", waiting for approval).

Part 6

The points engine

This is the mechanism the whole gamification stands on, so it got built early and tested hardest (PR #39). The rule from your scoring guide:

points = difficulty × multiplier(rating)
Example: a difficulty-3 task graded 4 ("Foarte bun") earns 3 × 2 = 6 points for each assignee.
RatingMeaningMultiplier
1Foarte slab — done wrong, hurt the team−1 (subtracts!)
2Insuficient0
3Bun+1
4Foarte bun+2
5Excelent+3

How it's built, piece by piece:

  • The ledger (points_ledger). Think of it as a bank statement: one row per points event — "+6 from task 12", "+5 manual award from Radu", "−3 sanction from BC". A member's total is never stored anywhere; it's always the sum of their statement. Stored totals drift out of sync; a sum cannot.
  • Triggers — the robot clerk. A trigger is a small program the database runs by itself when something happens. When a Responsabil grades a task, the trigger instantly writes one ledger row per assignee, with the computed points. If the grade is later corrected, it updates the existing row (no duplicates — enforced by a uniqueness rule, not by trust). If a grade is removed, the rows disappear. If someone joins a task after grading, they get their row; if they're removed, it's taken back. Nobody has to remember any of this — the database does it, every time, atomically.
  • Views — live spreadsheets. member_points (everyone's total), leaderboard (ranked, active members only), dept_cup (department totals for the cup) are views: saved queries that always compute from the ledger at the moment you look. They can never be stale.
  • Append-only for humans. No app user — not even BC — can edit or delete ledger rows. BC can add a signed sanction or award; history is never rewritten. That's what makes the ledger trustworthy at AGO time.
Part 7

Security, in layers

This app will hold personal data of ~200 students, so security wasn't an afterthought — it's four of the six migrations. The design is layered: each layer assumes the one above it might fail.

Layer 1 — Who gets in: invite-only (ADR-0003)

There is no "Register" button. Public sign-up is disabled at the server; accounts come into existence only when BC invites someone — a magic link arrives by email, they click it, they're in. No passwords to create, distribute, or leak. Volunteers keep using their personal Gmail; later they can attach "Sign in with Google" to the same invited address.

Layer 2 — Who is who: the JWT with claims (PR #40)

In plain words — JWT

When you log in, the server hands you a signed token (a JWT) — like a festival wristband. Every request you make shows the wristband. Ours gets stamped, at login, with your role, your level, your departments and your teams. The stamp is cryptographically signed, so it can't be forged — and because the information rides inside the token, the database can check permissions without extra lookups on every row. Fast and safe.

The stamping is done by a small function (the "claims hook") that runs at token time. Crucially, it fails closed: an account that was never invited, or a member whose status isn't active, gets no stamps at all — and an unstamped wristband opens nothing.

Layer 3 — Who sees what: Row-Level Security

In plain words — RLS

Row-Level Security is a bouncer living inside the database. Every query, from anyone, gets filtered row by row against written policies: "you can see this task because it's your department's; you cannot see that one." The permission logic exists in exactly one place — the database — so there is no bug in any screen, today or ever, that can leak data the policies forbid. Even a stolen API key sees only what the policies allow that identity.

PR #41 flipped the whole database to deny-by-default: RLS on, zero policies — a logged-in user could read nothing at all, from any table. Verified by tests, table by table. Then PR #42 opened exactly the intended slices for tasks and points:

  • a member sees their own tasks, their department's, their team's, and open-to-claim tasks — a Responsabil (level ≥ 4) sees and manages everything;
  • anyone may claim an open task — but only for themselves; the database rejects claiming in someone else's name;
  • you always see your own points (including sanctions — transparency is in the mandate); a Responsabil sees their department's; BC sees all;
  • awards need level ≥ 4, sanctions are a BC act (level ≥ 6), and both must be signed by whoever gives them;
  • requests are filed as yourself, always start "pending", and decisions are signed by the decider.

One real hole was found and closed along the way: the platform's default permissions quietly allowed any client key to TRUNCATE tables — an "empty the whole table" command that RLS does not govern. That privilege is now revoked everywhere, and anonymous (not-logged-in) visitors lost every last permission, which is correct for an invite-only app.

Part 8

The safety net: 101 tests

In plain words — automated test

A test is a tiny script that sets up a situation, does the thing, and checks the outcome: "create a difficulty-3 task, grade it 4, assert the assignee got exactly 6 points." Run one by hand, it proves today's code works. Run all of them automatically on every future change (that's the CI robot), and they become a tripwire: anyone — you, a volunteer, an AI — who accidentally breaks the points formula or opens a data leak gets a red ✗ before the change can reach main.

The suite currently holds 101 tests in 4 files, and they encode the project's promises:

  • Points engine (26) — the multiplier table; grading writes correct rows; a rating of 1 subtracts; re-grading updates instead of duplicating; un-grading restores totals; sanctions reduce them; leaderboard and dept cup sum correctly.
  • Claims hook (17) — a BCE token carries level 5 and the right departments; existing token data is preserved; un-invited and inactive users get nothing; only the auth server may call the hook.
  • Deny-by-default (30) — with bait data planted, a normal user reads zero rows from every single table and view; writes are rejected; anonymous is locked out; no table may ever lack RLS (this one guards all future tables too).
  • Per-role policies (28) — four simulated people (two Voluntari from different departments, a Responsabil, a BC member) each try everything they should and shouldn't be able to do.

An honest detail from this week, because it teaches something: one of my own security tests initially passed for the wrong reason — the "forbidden" insert targeted a task the user couldn't even see, so it inserted zero rows and nothing was there to deny. The lesson: a test must fail when the rule is removed, or it's decoration. It was rewritten against a visible task, and now it genuinely bites.

Part 9b

Update — August 20 to 24: the rest of the backend

Five more days, thirteen more merged pull requests (#122–#141), and the backend went from "core schema, half-secured" to "every v1 table exists, every table is correctly locked down, real accounts work end to end, and there's a believable demo sitting on staging." This part covers what changed and, more importantly, why two of these took longer than planned — both are worth understanding, not just skimming past.

The rest of the schema, and the rest of the policies

The four tables Part 5 didn't get to — events + event_attendance, announcements + announcement_reads, notifications, notif_suppression + push_tokens — all landed, each locked at birth the same way tasks were. Then their policies followed: who can read/write a calendar event depends on its scope (org-wide, department, team, and a special case for recruit-only teams); who reads an announcement is everyone, who posts one is level ≥ 4; notification suppression means BC and BCE stop drowning in routine task/event noise but still hear about their own work. A new helper, auth_is_member(), was added specifically to make "you must be an actual member, not just logged in" easy to write and easy to spot when it's missing — which turns out to matter a great deal (next section).

In plain words — the difference between "logged in" and "a member"

Supabase's built-in authenticated role means exactly one thing: this request presented a valid login token. It does not mean the person behind it was ever invited, and — this is the subtle part — it does not mean they're still active. A member BC deactivates keeps their old login token, and that token keeps working, until it naturally expires (up to an hour later). So "logged in" and "a real, current member" are two different facts, and a policy that only checks the first one is checking the wrong thing.

The security audit: 12 policies fixed before anyone got hurt by them

Before writing more code, a full pass was made through every existing RLS policy asking one question: could a session that's authenticated but has no real membership — never invited, or deactivated — still get in? Twelve policies said yes. The worst one was serious: a deactivated member could still insert themselves onto an already-graded open task, and because the points trigger runs automatically and doesn't know the difference, it would have handed them points they had no business earning.

All twelve were fixed in one migration, and — this is the important part, the part that makes it a fix and not a promise — a permanent test was added that checks every table against a claims-less session and fails, by name, if any of them ever leak again. The rule is now written down as house rule 12: every policy on authenticated must be impossible to satisfy without real membership claims. This is exactly the kind of mistake that's easy to make once and then copy-paste eleven more times — which is what had happened — and exactly the kind of mistake a good test makes structurally hard to repeat.

Real accounts: the invite-member function, and what it took to trust it

The first Deno code in the repo: an Edge Function that lets a BC-level member type in an email and have a real account come into being — magic link sent, profile provisioned, department and team memberships attached, atomically. It's now proven over real HTTP, not just in theory: sign in as BC, invite an address, watch Mailpit receive the link, click it, land signed in with the correct role and level stamped on the token.

Getting there surfaced three bugs worth naming, because each one teaches something:

  • Re-inviting an existing address didn't fail — it returned the existing user. The provisioning step then hit a duplicate-key error and the automatic cleanup code, written to undo a failed invite, deleted a real, existing member's account as collateral damage. Fixed by checking for the existing account first, and by never deleting on that specific error again.
  • A typo in an email would have gone out before any validation ran. Department and team IDs are now checked before the invite is sent, not after.
  • The email provider itself was accidentally switched off while tightening an unrelated setting — the two settings are both called "enable_signup" in different sections of the config and mean opposite things. With the provider off, every login failed, not just new invites. This is now a documented trap (docs/backend/auth-config.md) with the exact two lines to check.

The function is also now genuinely testable — its logic sits behind a small interface so eleven scenarios, including all three bugs above, run as automated tests in under a second, with no real server involved.

Demo data — and the gap that would have embarrassed us on September 15

Eight logins, one per role, password parola123; sixteen tasks in every status with real graded history so the leaderboard looks alive; a calendar covering every visibility rule; five announcements; notifications with suppression visibly at work. All of it built by letting the real triggers run — grades are set and the points engine computes the ledger itself, the same as it will for a real task, which means the demo doubles as a live proof the engine works.

Then a genuinely important gap turned up while double-checking staging: merging this data changed nothing there. The deploy step that pushes migrations to staging on every merge does exactly that — pushes migrations — and demo data isn't a migration, so it had never once reached the shared server. Staging had the correct schema and zero rows in it. On its own, that's not a bug; it's just an incomplete story. But the September 15 demo runs on staging, and an app with a perfect schema and no data doesn't show an error — it shows nothing, silently, which is the one failure mode nobody notices until they're standing in the room.

The fix has two parts. First, the demo data file was rewritten to be safely re-runnable against a live database — it clears only the eight demo accounts and everything they own before re-inserting them, carefully ordered so real people's data (anyone testing on staging) is never touched. Second, a manual, guarded workflow was added that applies it to staging on request: it refuses to run unless you type the staging project's ID to confirm the target, and refuses again if the connection string doesn't match — nothing about seeding a shared server should ever happen by accident. It's a deliberate button, not a side effect of a merge, and CI itself now applies the file twice on every PR to prove it stays safe to re-run.

Where the number 266 comes from

The test suite grew from 101 tests in 4 files to 266 tests in 15 files: the four new tables each got their own suite, the claimless-session sweep got its behavioral guard, the invite function got its 11, and the demo seed got a suite of its own proving the leaderboard it produces is the one everyone expects.

What this unlocks

The backend for v1's entire core scope is now complete and secured. The frontend mini-spec — folder layout, routes, data-fetching conventions, how the mockup's theme tokens carry over — is written, so the next thing to exist in the repo is the actual application people will click on. That starts now.

Part 10

Lessons picked up on the way

  • Setting GitHub secrets needs a real terminal. The first attempt stored three empty secrets because the command was run through a prompt with no keyboard input attached. Symptom: CI said "secrets not configured" even though they existed. Fix: set them in the browser, or pipe from the clipboard: Get-Clipboard | gh secret set NAME.
  • Windows sometimes reserves the local database ports. If supabase start ever fails with "port not available / access permissions", Windows' NAT driver grabbed the port range after a reboot. Fix, in an administrator PowerShell: net stop winnat then net start winnat.
  • Access tokens should outlive your critical dates. The staging token was set to ~90 days instead of 30, so it can't expire in the middle of demo week. Expiry date noted in Bitwarden with a calendar reminder.
  • The staging job "skipping" on a PR is correct. Deploys happen only on merge to main — unreviewed branches must never touch the shared server.
