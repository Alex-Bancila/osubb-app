1 · The mission

What we're building, in two minutes

One internal app for the whole organization: every member sees their tasks, earns points when work is graded (difficulty × quality — the official scoring guide), follows the calendar and RSVPs, reads announcements, gets notifications. BC manages roles, awards and sanctions in the same place. Promotions up to Membru Activ happen automatically (time / points thresholds); everything above stays a BC decision.

It replaces the spreadsheet-and-WhatsApp system with something that is always up to date, visible to exactly the right people, and fun enough (leaderboard, dept cup 🏆) that people actually use it.

Three dates matter: September 15 — full demo for BC · October 1 — live for the ~20 BC/BCE members · November — the whole organization, timed with recruitment. Version 1 is deliberately small so a student team actually hits these dates; QR check-in, native forms, calendar sync and phone-store apps are all planned for later phases, in writing.

3 · The stack

The technologies — what each is, why we chose it, how you'll use it

Git + GitHub

version control · collaboration · the backlog

What: Git records every change to the code as a snapshot ("commit") with a message; GitHub hosts the shared copy plus our task list (Issues) and code review (Pull Requests). Nothing important lives only on someone's laptop, and anything can be undone.

Why: it's the universal standard — every internship and job you'll ever apply to uses it. For us specifically: review-before-merge is how a team of beginners ships safely, and the issue tracker is our project plan.

How you'll use it: git checkout -b feat/my-task → edit → git commit → git push → open a Pull Request → I review → merge. You'll do this loop so often it becomes muscle memory. Issues labeled max-1h are your menu; each contains its own instructions.

Docker

runs the entire backend on your laptop, identically for everyone

What: Docker packages a piece of software together with everything it needs to run — the exact OS libraries, the exact database version — into a container: a small, isolated, disposable copy of a whole machine. When you run npx supabase start, it isn't installing a database on your computer; it's downloading and starting eight or nine containers (Postgres, the Auth server, the API gateway, Studio, Mailpit, and a few more) that together are Supabase, wired up to talk to each other.

Why: without it, "install Postgres 17.4 with these exact extensions, this auth server, this API layer, configured to match production" would be an afternoon per laptop, and a different afternoon for every OS. With it, everyone on the team — Windows, Mac, Linux — runs the same backend, because a container doesn't care what's installed around it. It's also the reason nothing you do locally can damage anything real: containers are throwaway. Delete them, they're gone; nothing on your actual machine was ever touched.

How you'll use it: mostly you won't think about it directly — npx supabase start/stop manages the containers for you. What you do need: Docker Desktop installed and running (there's a whale icon in your system tray/menu bar — if it's not there, nothing else in section 5 will work) before you run any Supabase command. If a command ever says "cannot connect to Docker", that whale isn't running yet.

Supabase

the entire backend: database + login + server functions

What: a hosted backend service built on PostgreSQL, the world's most trusted open-source database. Supabase gives us the database, the login system (magic links — no passwords!), auto-generated APIs, and small server functions, all in one. Locally, the exact same stack runs on your laptop in Docker (see above).

Why: we compared it against Firebase and building our own server. Supabase won because (1) it's just Postgres — real SQL, a skill worth learning, no vendor lock-in; (2) its Row-Level Security is a perfect fit for our 8-roles × 5-departments permission model; (3) the free tier covers development, and production costs ~$25/month total. An NGO budget likes that.

How you'll use it: three commands, honestly: npx supabase start (boot the local backend), npx supabase db reset (rebuild the database from scratch, migrations + demo data — your safety net: you literally cannot break anything permanently), npx supabase test db (run all tests). Plus two local websites: Studio at 127.0.0.1:54323 — a visual browser for your database — and Mailpit at 127.0.0.1:54324 — a fake inbox that catches every email the app sends locally.

SQL migrations

how the database changes, safely

What: we never click around editing the database by hand. Every change to its structure is a numbered file of SQL in supabase/migrations/. Every environment — your laptop, mine, the test server, production — replays the same files in the same order and ends up identical.

Why: "it works on my machine" dies here. Database structure becomes code: reviewable in a PR, versioned in git, reproducible forever. It's also how professionals do it everywhere.

How: npx supabase migration new my_change creates the file, you write SQL in it, db reset applies it. The issue you picked tells you exactly what SQL — usually adapted from the architecture spec.

Row-Level Security (RLS) + JWT claims

who sees what — enforced by the database itself

What: RLS is a bouncer living inside Postgres: written policies filter every query row by row ("your department's tasks: yes; another's ledger: no"). When you log in, your token (JWT) gets stamped with your role, level, departments and teams, and the policies read those stamps.

Why: permission logic lives in exactly ONE place. No bug in any screen — today or two years from now — can leak data the policies forbid. For an app holding personal data of 200 students, this is the difference between "we hope it's fine" and "it's enforced" — and we proved the difference matters: an audit this week found 12 policies that only excluded logged-out visitors, not un-invited or deactivated ones, and closed every one.

How: mostly you'll just benefit: your screen queries return exactly what the logged-in user may see, automatically. When you do write a policy (some ≤1h issues are policies), you copy the pattern from an existing one and write tests proving who can't see what.

pgTAP tests + GitHub Actions (CI)

the safety net that lets beginners ship

What: pgTAP is how we write database tests ("grade a difficulty-3 task with rating 4 → assert exactly 6 points"). GitHub Actions is the robot that, on every PR, builds a fresh database from zero, applies all migrations, and runs all 266 tests. Red ✗ = not mergeable. Green ✓ = safe.

Why: because of this robot, you cannot break the app. Worst case, your PR goes red and you try again — nothing bad ever reaches the main code or the servers. This is what makes it safe to hand real work to new contributors in week one.

How: run the same checks locally before pushing (db reset + test db); when your issue says "add tests", copy an existing test file's structure — fixtures, action, assertions.

Deno (Edge Functions)

the small amount of logic too privileged for the database or the client

What: Deno is a JavaScript/TypeScript runtime, like Node.js but simpler and more secure by default. Supabase runs our server-side functions on it — right now, exactly one: invite-member, the function BC calls to invite someone.

Why: RLS answers "who can read/write which row", but "send an email inviting a brand-new person" needs a privilege no logged-in client should ever hold (the ability to create accounts). That belongs in a small, auditable server function, not scattered in the frontend.

How: you likely won't touch this early on — it's one function, already built and tested. If you do: the logic lives behind a small interface (deps.ts) so it can be tested without a real server, which is how its 11 tests run in under a second.

React + TypeScript + Ionic (+ Capacitor later)

the user interface — starts this sprint

What: React builds the interface out of components; TypeScript is JavaScript with types (the editor catches your mistakes before you run anything); Ionic provides polished mobile-feeling components (tabs, lists, dialogs); Capacitor can later wrap the same app into real Android/iOS store apps without rewriting.

Why: our "desktop" is really a browser and our members live on phones → one web codebase that works everywhere, installable as an app (PWA), store apps later for free. React+TS is also the single most employable frontend skill you can practice right now. (We seriously evaluated Flutter — decision and reasoning written down in ADR-0002.)

How: npm run dev inside app/, edit a component, the browser refreshes instantly. Screen issues are sliced ≤1h: "render this list", "add this button". Two helpers do the heavy lifting: TanStack Query (fetching + caching + loading/error states) and AG Grid (the powerful tables for tracker & directory). Exactly how we use all of this is written down in the frontend mini-spec — read it once before your first screen issue.

Cloudflare Pages · Bitwarden · Claude

hosting · secrets · the AI teammate

Cloudflare Pages will host the frontend for free once it exists — every merge deploys automatically; every PR even gets its own preview link reviewers can click.

Bitwarden holds all passwords/keys/tokens. Iron rule: secrets never go into git — git history is forever. If you ever see a key in code, say something immediately; that's a save, not a mistake.

Claude (AI coding agent) is a teammate here: issues labeled ready-for-agent are specified precisely enough that Claude can implement them under review. It built most of the current backend — every line still went through PR review, tests and CI like anyone else's work. You'll learn to drive it in training session 2; "supervising an AI + reviewing its output" is a genuinely modern skill.

One issue = one branch = one PR. Small, boring, unstoppable. One extra rule learned the hard way: never open a PR whose base is another unmerged branch (a "stacked" PR) — it cost us two recoveries. If your work depends on something not yet on main, ask first.

  • Sprints: two weeks of building + a 3-day review buffer. Weekly 30-minute sync; quick async check-ins Monday & Thursday in the group chat. Demo at every sprint end.
  • Review: I review every PR while we ramp up; after your ~5th merged PR we move to peer review (I stay on migrations & security). Reviews are teaching, not gatekeeping — expect comments, they're the fastest way to learn.
  • Definition of done: migration applies on reset · tests pass (and would fail if your feature were removed) · CI green · the issue's checkboxes ticked · PR says Closes #n.
  • Where everything is written down: CONTEXT.md (our vocabulary) · docs/adr/ (why each big decision) · docs/roadmap.md (the calendar) · docs/team/team-plan.md (this operating model) · docs/agents/onboarding.md (the "continue from here" guide, codebase tour + known traps) · docs/backend/implementation-issues.md (the backlog map) · the architecture spec in docs/superpowers/specs/. If you wonder "why is X like this?" — the answer has a file.

Set up your laptop — do this before you leave today

Install (all free): Git (git-scm.com) · Node.js LTS (nodejs.org) · Docker Desktop (docker.com — start it and let it finish, then leave it running) · GitHub CLI (cli.github.com) · VS Code (code.visualstudio.com). Make a GitHub account if you don't have one and send me your username for repo access.

# 1 · connect GitHub and get the code
gh auth login                        # browser login, defaults are fine
git clone https://github.com/Alex-Bancila/osubb-app.git
cd osubb-app

# 2 · boot the backend (first run downloads ~2–3 GB of Docker images, be patient)
npx supabase start

# 3 · build the database + run every test
npx supabase db reset                # applies migrations, then seeds demo data
npx supabase test db                 # expect: "All tests successful" ✅ (266 tests)

# 4 · look around
#   Studio (database browser):  http://127.0.0.1:54323
#   Mailpit (fake email inbox): http://127.0.0.1:54324
#   Try logging into the app once it exists with voluntar@demo.osubb / parola123

If all four steps worked: you are fully set up — you just built the entire OSUBB backend from source, populated it with realistic demo data, and proved it correct on your own machine.

If something breaks

"Cannot connect to Docker" → Docker Desktop isn't running; start it, wait for the whale, retry.

"Port is not available / access permissions" (Windows) → Windows reserved our ports after a reboot. In an administrator PowerShell: net stop winnat then net start winnat, retry.

Anything else → screenshot in the group chat. Setup problems are normal and are never "your fault".

7 · FAQ

Questions you'll probably ask

"What if I break something?"

You can't, structurally. Your work happens on a branch; the robot tests every PR on a throwaway database; nothing reaches main or the servers without a green ✓ and a review; and your local database rebuilds from zero with one command. The system is designed to make experimenting safe.

"Why no passwords anywhere?"

Sign-up is disabled — accounts exist only by BC invitation, delivered as a magic link by email. Nobody generates, distributes, forgets or leaks passwords. And even an account that somehow authenticates without being invited (or was invited and later deactivated) sees exactly zero rows — the database denies by default, and we specifically re-audited that this holds for deactivated members too, not just strangers (ADR-0003).

"Why not Firebase like every YouTube tutorial?"

Firebase is a document store with permission rules bolted on; our app is relational (members ↔ departments ↔ tasks ↔ points) with a subtle 8-role permission model. Postgres + RLS fits that natively, SQL is a better skill to learn, and there's no lock-in. The full comparison is written down in the tech-stack doc and ADR-0001.

"Why can't I just edit the database in Studio?"

Locally, for looking around — absolutely, that's what Studio is for. But changes that should persist must be migrations, or they exist only on your laptop and die at the next reset. Rule: Studio to explore, migrations to change.

"An AI wrote the backend — is that safe? What's left for me?"

Every AI-written line went through the same review, tests and CI as human code — that's the point of the pipeline: it doesn't trust anyone. It even caught its own mistake once — a security audit found and fixed 12 leaky policies before they reached real data. What's left for you is plenty: the entire UI, the remaining policies, reviewing, and learning to direct AI effectively — which is how software is increasingly built everywhere. You're not competing with the tool; you're learning to conduct it.

"What do I do when I'm stuck?"

15-minute rule: try for 15 minutes, then ask in the chat with a screenshot and what you tried. Asking early is a team norm here, not a weakness — it's literally in the team plan.
