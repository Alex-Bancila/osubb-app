# Backend conventions

A reference for writing Supabase migrations in this repo — not a tutorial. Each section states the rule and points at one real example on `main`. Where the code currently has two shapes, the rule below picks one and names the grandfathered exceptions so nobody "fixes" them casually. `supabase/tests/conventions.test.sql` machine-checks six things: every `security definer` function in `public`/`private` pins `search_path` to the empty string; nothing in `public` or `private` is executable by `anon`; no trigger function or `require_*` helper is executable by `authenticated`; every `public` view is `security_invoker` except `member_points`/`profiles_contact`; `anon`/`service_role` have no `usage` on `private`; and (#520, ADR-0009) no function body or policy expression in `public`/`private` mentions `groups.category` except the named presentation writers and projection — it is a presentation label, never an authority, visibility, membership, notification or Cup input. Because that sweep reads `pg_get_functiondef`, the word must not appear inside a function body even in a comment: put such prose in `comment on function`. It does **not** check the four-role revoke form, object naming, or the error-code table — those stay reviewed by eye against this page.

## 1. Migrations

Create every migration with `npx supabase migration new <snake_case_name>`; migrations are forward-only and additive (no editing a merged file — add another one). The first line is `-- #<issue>: <one-line purpose>`; further comments explain _why_ a choice was made, not what the SQL already says. Reference data (roles, Departments, rating/difficulty guides, notification suppression) lives in migrations; demo data lives in `supabase/seed.sql` (house rule 6). `supabase/migrations/0001_core_schema.sql` is the one non-timestamped file in the directory and is never renamed.

Example: `supabase/migrations/20260910173341_departments_diverse_secretariat.sql` (first line `-- #310: coordination structures Diverse (Department Teams it, interne) and Secretariat; retire the legacy 'it' department.`).

## 2. Command shape

A client-callable write is two functions. `public.<verb>_<noun>(…)` is `security invoker`, `set search_path = ''`, and does nothing but call `private.<verb>_<noun>_impl(…)`. The `_impl` function is `security definer`, also `set search_path = ''`, fully-qualifies every name, and does the real work. The actor is always `(select auth.uid())` — never a parameter a caller could spoof. A `private.require_<authority>(…) returns uuid` helper performs authorization and returns the actor; the command locks its target row `for update` first, re-validates the actor's live membership `for share`, then mutates, and returns the affected row.

**Lock modes are not interchangeable — read this before writing a command that can touch two rows of one table.** The target row is `for update`. **Any parent row the command also reaches — in the Tracker, a Subtask's Umbrella — is `for no key update`, never `for update`**, and a row that may itself be a parent (`cancel_task`'s and `complete_umbrella_task`'s target) takes the weaker mode unconditionally rather than branching on kind. The reason is a lock nobody writes: `private.evaluate_task` inserts `task_activity` and `notifications` rows that _name_ the Umbrella parent, and every such insert takes an implicit foreign-key `FOR KEY SHARE` on that parent row. `FOR KEY SHARE` conflicts with `FOR UPDATE` and with nothing else — so a command holding a parent `for update` while reaching for a child forms a real ABBA cycle against a concurrent evaluation of that child, and Postgres answers `40P01`. This is not theory: it was **reproduced under mutation three times** (#338, #339, #340), and the one command that kept `for update` on a parent (`create_task`, fixed in the wave closeout) stalled every concurrent evaluation under its Umbrella even though it could not deadlock. The weaker mode costs nothing: `FOR NO KEY UPDATE` still conflicts with itself and with `FOR UPDATE`, so commands still serialize against each other, and the only unique index on `public.tasks` is its primary key, so a write never has to upgrade the lock afterwards. Child rows a command only _reads_ are `for share`. When a test probes a lock, note that `extensions.pgrowlocks` reports the mode as the exact string **`For No Key Update`** — plain `No Key Update`, without the leading `For`, is the _updater_ string, reported only once a write has actually landed on the row.

**Where a check goes is part of the contract.** A value that violates a CHECK constraint's range, or is blank or null where a constraint forbids it, is malformed for **every** caller: no one could ever have succeeded with it, so it is raised at **step 1, before the gate** — `PT400`, ahead of any `42501`. Validation that can only be judged against the loaded row — its kind, its status, its Origin, whether a referenced id belongs to it — depends on authority to be meaningful and belongs at **step 5**, under the lock. The three commands that share `private.evaluate_task` all hoist the same three inputs (`evaluation_note_required`, `invalid_difficulty`, `invalid_rating`) for exactly this reason; `create_task`'s `deadline_required` stays at step 5 because whether a deadline is required depends on the Task's kind; its `title_required` is unconditional and stays there only because no constraint forbids a blank title (`title` is merely `not null`), so it is not malformed-for-everyone in the constraint sense and the rule permits either position. Sibling commands over one core must agree: a claimless caller answered `PT400` by one and `42501` by another is a bug in the pair, not a style difference.

**One accepted deviation from the `require_*` discipline, recorded so nobody "fixes" it by accident.** Every command routes authority through a `require_*` helper that holds the actor's `profiles` row **and** the membership row its authority rests on `for share`, so a concurrent deactivation serializes behind the decision instead of committing underneath it. `private.create_completed_work_request_impl` (#344) is the one exception: its membership test is three bare `exists` sub-selects with no lock. That is accepted, not overlooked — it is a membership-only check by a non-privileged actor _filing_ a request, and the worst race outcome is a `pending` Request naming an Origin the requester left an instant ago, which a decider must still act on and which the Request row itself records. The discipline is binding wherever the actor **exercises** authority; `approve`/`reject` therefore keep it in full. (Its step comment in that migration labels the block "3." when it is step 4 — a merged migration is never edited, so the correct numbering is recorded here instead.)

**Closing a Candidate Queue writes no activity row of its own.** `private.close_task_queue` only closes; each caller decides what to log, and the shipped rule is narrower than "an automatic close writes none": `public.set_task_queue` is the **only** command that logs a `queue_closed` activity row (with `details.closed_candidates`). `select_task_candidate` folds the count into its `candidate_selected` row and `cancel_task` into its `cancelled` row — both manual closes, both passing the actor as `decided_by` — and `private.evaluate_task`, the automatic close and the only caller passing `decided_by = null`, records the close nowhere on the Task's own timeline, because the `evaluated`/`unfulfilled` row already says why the queue shut. A consumer building a Task timeline reads `closed_candidates` off whichever of those rows is present.

Grants follow §4's function idiom: `revoke execute … from public, anon, authenticated, service_role` on every function in the pair — wrapper, `_impl`, and the `require_*` helper — then `grant execute … to authenticated` back on the wrapper and the `_impl` only (the invoker wrapper calls the `_impl` as the caller, and `private` is never listed in `supabase/config.toml`'s `api.schemas`, so PostgREST cannot reach it directly). `require_*` helpers and trigger functions get no grant back at all — only the command that calls them needs to run them, and it runs as `security definer`.

Once a command owns a table's writes, the same migration also revokes `insert, update, delete` on that table from `authenticated` — new `public` tables inherit `select, insert, update, delete` for `authenticated` from `20260819171628_capabilities_and_rls.sql`'s default privileges, so without this revoke the RLS-gated command would sit next to a still-open direct write path. This makes the command the table's only write path, as house rule 13 requires.

Example: `supabase/migrations/20260909151741_project_membership_commands.sql` — `private.require_active_project_lead` locks the Project, then the actor's Profile, before `private.add_project_member_impl` / `remove_project_member_impl` / `grant_project_responsible_impl` / `revoke_project_responsible_impl` mutate, each behind a one-line `public.*` SQL wrapper; the same file's line 270 revokes `insert, update, delete on table public.project_members from authenticated`. Same table-DML revoke in `supabase/migrations/20260909140036_project_lifecycle_commands.sql:148` (`public.projects`) and `supabase/migrations/20260910154759_independent_team_membership_commands.sql:170-171` (`public.team_members`, `public.teams`).

**No grandfathered direct-definer commands remain:** #370 moves `create_event` behind an invoker wrapper; #345 retired the other legacy command.

## 3. Errors

Two syntaxes are both in current use, split by error code family — pick the one that matches the code, not either at random. A standard Postgres SQLSTATE (`42501` not authorized, `23514` a trigger-enforced invariant) is raised `raise exception using errcode = '<code>', message = '<reason>';`. An app-defined `PT4xx` code is raised `raise sqlstate '<code>' using message = '<reason>';`. Every `<reason>` is `snake_case` going forward.

Code table:

| Code    | Meaning                       | Reason shape                                                                                                                                                                                                                 |
| ------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `42501` | not authorized                | `<scope>_forbidden` — `task_command_forbidden`, `task_manage_forbidden`, `task_evaluate_forbidden`, `task_executor_forbidden`, `request_decide_forbidden`                                                                    |
| `PT400` | invalid input or precondition | `invalid_<x>` / `<x>_required` / `<x>_not_allowed_for_<y>` — `invalid_difficulty`, `invalid_origin`, `deadline_required`, `evaluation_note_required`, `executor_not_allowed_for_public`                                      |
| `PT404` | not found **or not visible**  | `<subject>_not_found` — `task_not_found`, `request_not_found`; never let a caller distinguish hidden from missing, and never mint a `*_not_visible` twin                                                                     |
| `PT409` | state conflict                | `<subject>_<state>` / `<state>_<subject>` — `task_terminal`, `task_not_in_review`, `nothing_to_update`, `already_executor`, `candidate_not_pending`, `subtasks_not_terminal`, `umbrella_cancelled`, `task_already_evaluated` |
| `23514` | trigger-enforced invariant    | `snake_case` reason going forward                                                                                                                                                                                            |

The reason names **what the thing is, not which command took it** (Ruling 28). A blank note that becomes an _Evaluation's_ note is `evaluation_note_required` in all three commands that write one (`complete_task_review`, `mark_task_unfulfilled`, `approve_completed_work_request`); a note that is only a decision or feedback note is `note_required` (`return_task_to_progress`, `reject_completed_work_request`); a reason recorded on a row is `reason_required`. Two commands answering the same condition must use the same string, and one command must not mint a distinct string per branch when that would reveal which branch fired — `reopen_task` deliberately reuses `task_evaluate_forbidden` for its local authority rule rather than leaking a narrower one.

Group and Calendar commands use `42501 group_manage_forbidden` / `calendar_manage_forbidden`; an unknown, archived, or unauthorized creation Group has the same Calendar error. Event content validation uses `PT400 invalid_event_title`, `invalid_event_type`, `invalid_event_interval`, `invalid_event_capacity`, `invalid_event_min_level`, and `event_group_required` before authority checks — naming no Group at all is a malformed argument, not a refusal, on both `create_event` (#370) and `update_event` (#248), which is a full-state replace and therefore always names one. **`event_group_required` is a deliberate name collision, one of two in the vocabulary** (the other is `subtask_origin_mismatch`: `PT400` from `private.create_task_impl` when the caller names a Subtask Origin that differs from its Umbrella, `23514` from `private.validate_task_hierarchy` when a row reaches the trigger that way — the same command-versus-invariant split): the same reason also exists as `23514`, raised by `private.sync_event_group_origin` when a row reaches the bridge with no Group at all. The `PT400` means "you did not say where" and the caller can fix it; the `23514` is a trigger invariant and means a bug. Since the frontend normalizes on the message rather than the code (below), keep the two apart by code until Wave 3 drops the trigger and collapses them. After authority, `event_min_level_below_group` and `event_min_level_above_actor` enforce the loaded settings; update/cancel use `PT404 event_not_found`, `PT409 event_cancelled`, and cancellation's `PT400 reason_required`. A hidden Task still returns `PT404 task_not_found` when a below-Minimum-Level caller attempts to express interest.

Wrappers never catch an error the `_impl` function raises — let it propagate. PostgREST maps `PT4xx` to the matching HTTP 4xx status; the frontend normalizes on the message, not the code.

Example: `supabase/migrations/20260909151741_project_membership_commands.sql` raises `42501` (`errcode` form) and `PT400`/`PT404`/`PT409` (`sqlstate` form) in one file. `23514` example: `supabase/migrations/20260909003930_project_manager_invariants.sql`.

**Grandfathered:** the six `23514` messages in `20260909003930_project_manager_invariants.sql` are full English sentences (e.g. `'active project managers must be active OSUBB members'`), not `snake_case` reasons — leave them as they are.

## 4. Grants and RLS

Every new table enables RLS in the migration that creates it (house rule 2). Every policy `to authenticated` contains `auth_is_member()` or `auth_level() >= N` — `to authenticated` alone only excludes `anon`, it is not a membership check (house rule 12; enforced by the claimless sweep in `supabase/tests/rls_deny_by_default.test.sql`). Views get `with (security_invoker = on)` except `member_points` and `profiles_contact`, whose `where` clause _is_ the security boundary — do not "fix" them to `security_invoker`, it breaks them for everyone they serve.

**Tables and views** follow one idiom: `revoke … from public, anon` followed by an explicit `grant … to authenticated, service_role`; never `grant … to anon`. The `private` schema gets `usage` granted to `authenticated` only — it is never exposed to PostgREST.

**Exception: gated leadership read surfaces grant `select` to `authenticated` only, not `service_role`.** `public.dept_cup` (#259) is the example: it is `security_invoker` over `private.department_cup_rows`, and `service_role` has no `usage` on `private` (machine-checked above), so a retained `grant select … to service_role` on the view could never return a row — it would fail `42501 permission denied for schema private` the moment it tried. Granting `service_role` `usage` on `private` to make the grant work is not an option either; that would punch a hole through the command boundary this schema exists to enforce. Do not "restore convention" by adding `service_role` back to one of these views.

**Functions follow a different idiom: revoke execute from everyone, then grant back only what is needed.** Every `create function` gets its own `revoke execute … from public, anon, authenticated, service_role`, then an explicit `grant execute … to <role>` for exactly the roles that must call it: the public wrapper and its `private.*_impl` each get `grant execute … to authenticated` (the `_impl` is called by the invoker wrapper as the caller); `private.require_*` helpers and trigger functions get no grant back at all — nothing should ever call them directly. None of the command migrations grant function execute back to `service_role`. This is not optional cleanup: Supabase's default ACL grants EXECUTE on new `public`-schema functions to `anon`, `authenticated`, and `service_role` explicitly, and Postgres grants EXECUTE to `PUBLIC` in every schema by default, so **a function without its own revoke is callable by all three roles the moment it is created** — `private` included. `supabase/tests/conventions.test.sql` machine-checks two slices of this: it fails CI naming any function in `public`/`private` still executable by `anon`, and separately naming any trigger function or `require_*` helper still executable by `authenticated`. It does not check `public` or `service_role` execute, or the four-role revoke form itself — that stays reviewed by eye.

Policy predicate helpers (`private.is_*`, `private.can_*`) follow the wrapper/`_impl` half of this idiom, not the `require_*` half: revoke from all four roles, then `grant execute … to authenticated` — they run as the calling role inside RLS policies and must stay callable by `authenticated` (e.g. `private.can_read_team`, `supabase/migrations/20260910210000_scope_team_policies.sql:75`). The `public.auth_*` JWT-claim helpers are an older, grandfathered variant of the same idea — see the list below.

**Grandfathered — older revoke shapes that predate the four-role form, verified against their migrations, not extended to new work:**

- Two-role revoke (`public, anon`), grant back to `authenticated` only: `in_my_dept` (`supabase/migrations/20260819172728_tasks_points_policies.sql:30-31`), `team_admits_recruits` (`supabase/migrations/20260822230203_event_policies.sql:31-32`), `set_event_rsvp` (`supabase/migrations/20260830122310_set_event_rsvp.sql:83-86`). (#318 dropped `is_assigned` and #345 the legacy claim command, so two entries left this list.)
- Two-role revoke (`public, anon`), grant back to `authenticated, service_role`: `rating_mult()` and the `public.auth_*` JWT-claim helpers, revoked and granted together in one statement (`supabase/migrations/20260910140508_grants_hardening.sql:44-57`).
- Three-role revoke (`public, anon, authenticated`, no `service_role`), grant back to `service_role` only: `member_level()` (`supabase/migrations/20260823132458_member_level_helper.sql:35-36`), `provision_profile()` (`supabase/migrations/20260822222258_provision_profile.sql:45-48`).
- Three-role revoke (`public, anon, authenticated`, no `service_role`), no grant back at all: `reject_manual_award()` (`supabase/migrations/20260910135327_remove_manual_awards.sql:23`).
- Three-role revoke (`public, anon, authenticated`, no `service_role`), grant back to `supabase_auth_admin` — outside the four roles, because the Auth hook calls it as that role: `custom_access_token_hook()` (`supabase/migrations/20260819163238_jwt_claims_hook.sql:59-61`).

New work follows the four-role form above, not any of these precedents.

**Do not try to close this with `alter default privileges`.** A per-schema `alter default privileges` cannot revoke the global `PUBLIC` grant, and a global revoke for the migration role would also strip the `pg_temp` helper functions the test suites create and call as `authenticated` (`supabase/tests/_helpers.sql`). The fix that actually works is the one above: an explicit revoke on every function, every time.

`supabase db lint --level warning --fail-on warning` must be green — CI runs it, so fix the warning; never drop `--fail-on warning` to make the noise go away. The step lints every schema, including the Supabase-managed `extensions` schema (pgTAP lives there); if a deliberate Supabase CLI upgrade ever surfaces warnings in that third-party code, scope the step to `--schema public,private` in the upgrade PR rather than weakening `--fail-on`. `db lint` only understands `plpgsql`: trigger functions and SQL-language functions are not linted. A common trap in a `plpgsql` command body: calling a `private.require_*` helper with a plain assignment (`v_actor := private.require_…(…);`) when the returned actor id is never read afterward — `plpgsql`'s "unused variable" check then fires. Use `perform private.require_…(…);` instead when only the authorization side effect matters (`supabase/migrations/20260909151741_project_membership_commands.sql:76`, `perform private.require_active_project_lead(p_project_id);`).

Example — tables and views: `supabase/migrations/20260910140508_grants_hardening.sql` (revokes all privileges on the leadership views from every role, then grants `select` back explicitly). Example — functions: `supabase/migrations/20260909151741_project_membership_commands.sql`, `supabase/migrations/20260910154759_independent_team_membership_commands.sql`, and `supabase/migrations/20260910180228_department_team_membership_commands.sql` each revoke execute on every function — wrapper, `_impl`, and `require_*` — from `public, anon, authenticated, service_role`, then grant execute back to `authenticated` only on the wrapper and `_impl`.

## 5. Naming

Policies are `<table>_<verb>[_qualifier]`, named after the table's real name, with verbs `read`/`create`/`update`/`delete`/`manage` and qualifiers like `self`/`leadership` (`projects_read`, `teams_create`, `team_members_read`, `member_departments_manage`). Constraints are `<table>_<what>_ck`; unique constraints are `<table>_<cols>_key`, or `<table>_<cols>_uidx` when built as a unique index; ordinary indexes are `<table>_<cols>_idx`; foreign keys keep Postgres' generated `_fkey`. Functions: `auth_*` for JWT-claim readers, `private.is_*` / `private.can_*` for boolean predicates, `private.require_*` for helpers that raise or return the actor, `private.<verb>_<noun>_impl` for command bodies. Triggers are `<table>_<what>` on functions named `private.<verb>_<noun>()`. Columns are `snake_case`, foreign keys end `_id`, timestamps end `_at`, actor columns end `_by`.

Example: `supabase/migrations/20260909151741_project_membership_commands.sql` (`private.require_active_project_lead`, `private.add_project_member_impl`); trigger naming in `supabase/migrations/20260909003930_project_manager_invariants.sql` (`projects_validate_leader_profile` on `private.validate_project_manager_state()`).

**Existing schema after #379:**

- Existing policy and CHECK constraint names were normalized by #379. New names follow §5; policy predicates and constraint expressions remain unchanged. The legacy `teams_id_dept_unique` unique constraint is now `teams_id_dept_key`.
- `tasks.type` and `profiles.tier` remain nullable free-form text; no finite vocabulary has been accepted. `push_tokens.id` remains a UUID identity. Restricting those domains or replacing existing identifiers is outside cosmetic naming cleanup.

## 6. Enum vs. `text check`

Use a Postgres `enum` only for the fixed vocabularies already declared in `0001_core_schema.sql` (`member_role`, `member_status`, `task_status`, `event_type`, `event_scope`, `noti_kind`, …; #345 dropped two more of them with the table they typed). Adding a value to an existing enum cannot run in the same transaction that then uses the new value, which makes enums a poor fit for anything still evolving. Any new or still-changing vocabulary — lifecycle states, modes, kinds — is `text not null check (col in (…))`, named `<table>_<col>_ck` per §5.

Example: `projects.status` and `project_members.project_role` in `supabase/migrations/20260908083829_projects_schema.sql` and `supabase/migrations/20260908174343_project_members_schema.sql`.

## 7. Timestamps

Every table gets `created_at timestamptz not null default now()`. `updated_at` is added only to tables whose rows are edited in place, and is maintained by the shared `private.set_updated_at()` trigger — until #368 lands that helper, the command itself sets `updated_at = clock_timestamp()` and its PR says so explicitly. Instants are always `timestamptz`, never `date` — Bucharest wall-clock rendering is a presentation concern, not a storage one (`tasks.deadline` is currently the one exception, a `date` column that #283 converts).

Example: `supabase/migrations/20260908083829_projects_schema.sql` (`created_at`/`updated_at timestamptz`, `updated_at >= created_at` check); manual `updated_at` maintenance in `supabase/migrations/20260909140036_project_lifecycle_commands.sql:109`.

## 8. Tests

Name suites `supabase/tests/<area>_<aspect>.test.sql`, using `CONTEXT.md` domain terms. Follow the skeleton in `supabase/tests/README.md`: `begin;` → `\set osubb_test_suite true` → `\ir _helpers.sql` → `set local search_path = public, extensions;` → `create extension if not exists pgtap with schema extensions;` → `select plan(N);` with the exact assertion count → `select * from finish(); rollback;`. Give each suite a recognizable fixture UUID prefix tied to its issue number, unique per fixture within the suite. For authorization, write one assertion per persona × operation, including **claimless, `anon`, and inactive-Member** denials — the claimless sweep needs one fixture row per table. Anything that serializes concurrent writers needs a two-session race via `pg_temp.test_race`. Write the test first and watch it fail: a test that stays green with the feature removed is not testing the feature.

Example: `supabase/tests/department_team_membership_commands.test.sql` (skeleton order, `select plan(40);`, fixtures prefixed `27900000-…` for #279).

**A `throws_ok` on a constraint violation names the constraint — never `null`** (Ruling 23). Postgres evaluates CHECK constraints in **name order**, so when a migration adds a constraint to a table an existing negative test already inserts into, that test can start passing on the _new_ constraint and silently stop testing the old one, with its assertion still green. #339 found exactly this: `tasks_cancel_reason_ck` sorts before `tasks_evaluation_inputs_ck`, so #312's cancelled-with-rating rule became untestable while its assertion kept passing. The rule has a second half: **whenever you add a constraint to a table, re-check every negative test that inserts into it.** Forty-plus `throws_ok(…, '23514', null)` assertions still stand across `supabase/tests/` — none of them shadowed today, all of them one new constraint away from being.

**A documented lock-probe gap is the fallback, not the first answer** (Ruling 19). Report honestly when a probe does not discriminate — a `pgrowlocks` assertion that stays green with the lock deleted proves nothing, and claiming otherwise is worse than admitting the gap. But before accepting one, check whether a two-session `pg_temp.test_race` (or a held `dblink` transaction plus a second session that must not block) would discriminate: where one is cheap and available, add the race instead. #337's probe was non-discriminating and its gap was correctly reported; the race that closed it took one fixture and flipped a stale `task_terminal` into `task_has_no_executor` under mutation. Accept a gap only when no discriminating probe exists — as when the vulnerable window is _before_ any lock is taken, which no lock-contention harness can hit deterministically.

### Local verification

`bash scripts/check-local-ci.sh` runs every gate `.github/workflows/ci.yml` runs, in CI's order, across all four jobs — repo, db, Edge Functions, frontend — and prints one PASS/FAIL line per gate. Two CI gates are deliberately **not** reproduced and the script says so on every run: the gitleaks secret scan (it needs an image pull) and the staging push (merge-only). Pass a job name (`repo`, `db`, `functions`, `frontend`) to run just that job. The `db` job runs `npx supabase db reset`, so the local stack must be up and whatever is in the local database is destroyed. It is a pre-push check, not a substitute for CI: house rule 7's "CI must be green" still means the real run on the pull request.

`bash scripts/smoke-tracker-commands.sh` runs the Task Tracker command set end to end — create a public Task, two members queue and one withdraws and rejoins, the manager closes the queue, the Executor starts and submits, the Reviewer returns and then completes, the award lands and is reversed by a reopen, an Umbrella completes over a completed and a cancelled Subtask, and a Completed-work Request is approved — every step through the `public` wrappers only, asserting the key fact at each one, and ending by proving `authenticated` cannot write a single Task table directly. It needs a freshly reset, seeded database (`npx supabase db reset` first), runs inside one transaction and rolls back, so it leaves the seeded data byte-identical. The wrapper uses `psql` when the host has one and otherwise `docker exec`s into the local stack's db container; on the docker path it splices `supabase/tests/_helpers.sql` into the SQL, because psql inside the container cannot see this repo on disk.

## 9. Pull-request checklist

- [ ] Migration header is `-- #<issue>: <purpose>`.
- [ ] New tables have RLS enabled in the same migration.
- [ ] Every `authenticated` policy contains a membership predicate (`auth_is_member()` or `auth_level() >= N`).
- [ ] Every `security definer` function sets `search_path = ''` and fully-qualifies names.
- [ ] Every new function revokes execute from `public, anon, authenticated, service_role`, then grants it back only to the roles that must call it (§4: `authenticated` for wrappers, `_impl`, and policy helpers; no grant at all for `require_*`/trigger functions).
- [ ] Once a command owns a table's writes, the same migration revokes `insert, update, delete` on that table from `authenticated` (§2).
- [ ] Errors use the code table in §3, not ad hoc codes or messages.
- [ ] Names follow §5 (policies, constraints, indexes, functions, triggers, columns).
- [ ] Tests ship in the same PR and fail if the feature is reverted.
- [ ] `npx supabase db lint --level warning --fail-on warning` is clean (§4).
- [ ] Touching a Group or roster write path? `group_mirror_retirement.test.sql` stays green, and only Group commands or rolled-back test fixtures write the roster.

## 10. Groups (ADR-0009 Wave 3)

**Groups and their rosters are the write master (#585/#586).** The four Group structure commands and three roster commands are the client write path; `private.appoint_group_member` is the shared insert core. The six legacy structure tables remain for compatibility until #590, including provisioning writes until #602 replaces them. Their old commands, Project-manager triggers, six forward-mirror triggers, profile Role rederivation trigger, and mirror helpers are gone. A write to a legacy row no longer changes a Group. `private.validate_group_member` enforces `23514 group_member_below_min_level` for every roster row; Member Role and Group Minimum-Level commands remove rows that fall below the threshold. A BCE promotion or demotion does not appoint or remove a Department Group Manager; `set_group_role` controls that row (ruling R15).

Tracker authority and visibility, Task commands, Completed-work Requests, Campaigns, Calendar, leadership metrics, and Department Cup traversal read `groups.path`, Group settings, and `group_members.group_role`. A Group Role flows down the ancestor path; ordinary membership stays on its own Group. With no Group Manager anywhere on that path, Responsibles manage peer Tasks, while evaluation of their own or another Responsible's work goes to BC/Moderator. No work command takes a legacy Origin argument.

`tasks.group_id`, `events.group_id`, `campaigns.group_id`, and `completed_work_requests.group_id` identify the owning Group, and since #579 they are the **only** Origin those rows carry: `group_id NOT NULL` plus its foreign key is the whole invariant. The legacy `dept_id` / `team_id` / `project_id` columns, `events.scope` and the `event_scope` enum, `campaigns.department_id`, the four `*_sync_group_origin` bridge triggers, the resolver `group_id_for_legacy_origin`, the shims `can_manage_origin` / `require_origin_manager`, the legacy `create_campaign(text, text)` overload and every legacy command argument are gone. Any Group — native or legacy-mapped — can own Tasks, Requests, Campaigns and Events. Do not reintroduce a legacy identity on a work row; a reader that needs a label reads the Group.

**The authority kit is the whole vocabulary.** New authority calls `private.group_role_of`, `is_group_member`, `has_group_manager`, `is_group_manager`, `is_group_responsible`, `can_manage_group_work`, `require_group_work_manager`, and `group_managers` (#520), or the Task-level predicates built on them (`can_read_task`, `can_manage_task`, `can_evaluate_task`, `require_task_visible`, `require_task_manager`, `require_task_evaluator`). Since #579 no work-authority function accepts a `dept_id / team_id / project_id` triple — the two shims that did are gone. Legacy ids left in `private` support compatibility reads and provisioning, never a second work-authority model.

The Wave 1 mirror and bridge history remains in the earlier migrations and ADR-0009. Review current catalog definitions when changing a Group consumer; do not infer live behavior from historical migration bodies.

**Trigger order on `tasks` no longer carries a bridge contract (#579).** `tasks_validate_hierarchy` fires on `insert or update of parent_task_id, group_id, kind` and `tasks_validate_campaign` on `insert or update of campaign_id, group_id`: a Group-only write fires both, with nothing to derive first. Any new `before` trigger on a work table that depends on the owning Group must list `group_id` in its `of` columns.

Use `path @> array[id]` for ancestry so the GIN index can serve it. Organization claims remain proof of a membership-bearing session, never current authority: Group predicates read live Profiles and rosters, and authority commands hold the Profile and deciding roster rows `for share` through their transaction. They avoid unnecessary authority locks on Group rows. The Organization Group is marked by `groups.is_organization`; its Automatic Membership is derived live and is not materialized in the JWT roster.

**The category-word check is deliberately stricter than a branch check.** `conventions.test.sql` rejects the standalone word `category` anywhere in a `public`/`private` function definition, including comments or projections, or in a policy expression. The former mirror writers are gone; one reader remains exempt: `public.my_groups()` (#576) projects the label for the Group pickers. It is a `security invoker` wrapper that decides no row itself — every row decision (the effective Group Role, `explicit`, `automatic`) lives in `private.my_groups_impl`, which stays under the sweep, and `groups_read` filters the rest. Group Category is a presentation label; business rules use settings and Group Roles.

**Two Group commands write the label, and only those two (#582, ruling R16).** `private.create_group_impl` chooses the Category at creation and `private.update_group_structure_impl` is BC's editor for it; both join the sweep's exclusion list beside the read-only projection. Their public wrappers `public.create_group` and `public.update_group_structure` are listed with them for a mechanical reason, not a second exemption: `pg_get_functiondef` renders a function's signature and the wrapper's argument is named `p_category`, because that is the name PostgREST publishes. Neither writer branches on the value — each only assigns what the caller sent — and the prose explaining that lives in `comment on function`, which the sweep does not read. `announcements.category` is a different column; a future function touching it needs the same treatment and the same review.

**`groups.parent_id` is immutable after insert (#582, ruling R20).** A Group's parent is chosen by `public.create_group` and never changes: there is no move command and there will be none, because Department Cup standings walk each Task's live `groups.path` and a path that never moves is what keeps attribution honest. A wrongly placed Group is archived and created again. `private.validate_group_hierarchy`'s UPDATE arm and `private.cascade_group_path` stay in the schema as tripwires rather than as machinery — no function may update `parent_id`, and #595 adds the conventions assertion that none does. The consequence for a command author: re-parenting is not a feature to extend, and a migration that needs a Group somewhere else creates it there.

**Capabilities are one server read (#576, ADR-0009 Decision 6).** `public.my_capabilities()` returns exactly one row of booleans from live rank and live Group Roles — all false without organization claims or an `activ` Profile — and the frontend's `useCapabilities()` reads it; there is no level map in `app/`. `manage_tasks` is `public.can_manage_tasks()` and nothing else, and `private.holds_any_group_role()` is the one definition of "holds a Group Role anywhere". A new capability is a new column there, derived from the same kit, never a threshold in TypeScript. `public.my_groups()` is the caller's effective Groups (R14): use `explicit or automatic` for membership questions (R31) and every row for manager-side controls.

**Fan-out reads the Group Audience, never `group_members` (#601).** Automatic Membership is never materialized — the Organization Group has no roster rows — so "who hears about this Group's Event or announcement" is `private.group_audience(p_group_id)` and nothing else: active roster Members of the Group and of every Group below it, plus, for each of those Groups with `automatic_membership`, every active Member at or above its `min_level`. A Group below the one asked about that is archived, or sits below an archived Group, contributes nobody. `private.event_notification_recipients` is that set plus the Event's `going` attendees, filtered through `private.can_read_event(min_level, member)` — the same predicate the `events_read` policy calls — so a Notification never carries an Event's title to a Member who cannot read the Event; announcement fan-out (#581/#68) calls the same helper. Task Notifications never use it.

The sweep reads `pg_get_functiondef`, which returns the body as written — so a function's own comments are inside what it checks, and the word cannot appear even in prose explaining why the function does not branch on it. Put that prose in a `comment on function` instead: the sweep does not read `obj_description`, and the explanation ends up where `\df+` and the catalog show it anyway.

The Wave 2 private-function roster grows **107 → 126**: five Origin bridge helpers (#519), eight Group authority helpers (#520), two net Request/Campaign helpers (#522), one Event creation implementation (#370), and three Event update/cancel/recipient helpers (#248). #521 and #523 replace existing functions without adding roster entries. Extending `private.notify` with its trailing optional Calendar link changes its signature, not the count. `tracker_grants.test.sql` pins the exact roster and grants; subsequent feature PRs must update that live pin rather than treating 126 as permanent.

**OD9 test-fixture exception:** owner-run tests and the smoke script may create native Groups or adjust Group settings such as Minimum Level inside a transaction that rolls back. This is fixture setup needed to prove Wave 2 behavior before public Group settings commands exist. It grants no client write path and permits no production data edit. All exercised work operations still call public commands; the smoke script labels its one direct setting fixture explicitly.

**Group structure is written by four commands (#582).** `public.create_group`, `public.update_group`, `public.update_group_structure` and `public.archive_group` are the only client write path into `public.groups`, and `private.require_group_manager` is the tier that gates them: `private.require_group_work_manager` and then, below level 6, `private.is_group_manager`, so a Group Responsible manages the Group's work but not its structure. Settings split by owner — structural (Category, both Cup flags, Automatic Membership, colour and short name, the Organization marker, a top-level Group's Minimum Level) is BC's and the Moderator's; operational (name, the Manager's display name, Applications and their Level, Shared Work Visibility, archiving a Child Group, a Child Group's Minimum Level) is the Group's Managers'. Both update commands are full-state replaces (OD5). Raising a Minimum Level above existing members refuses with `PT409 group_has_members_below_level`, the count in DETAIL, unless `p_confirm_removals` is true. `archive_group` refuses with `PT409 group_has_open_work` while the subtree holds a non-terminal Task or a pending Completed-work Request — archiving never cancels a Task — and otherwise cancels **every** future Event of the subtree and cascades the status in one `update … where path @> array[id]`, because `can_manage_group_work` reads the target Group's status alone.

**The Group roster is written by three commands over one core (#583).** `public.set_group_role`, `public.add_group_member` and `public.remove_group_member` are the only client write path into `public.group_members`, and `private.appoint_group_member(p_group_id, p_member_id, p_actor, p_group_role, p_position_title)` is the **only insert path** into it outside migrations' own backfills, rolled-back test fixtures — `add_group_member` is a thin gate over it, `set_group_role` calls it whenever the Member has no row yet, `private.create_group_impl` was re-issued to write its appointed Manager through it, and #602's provisioning calls it with the inviting BC as `p_actor`. `group_roster_commands.test.sql` sweeps `pg_get_functiondef` for a second writer and names it. Two tiers, not one: granting or removing `manager` is decided one level **up** — level ≥ 6 for a root Group, the **parent's** Group Managers for a Child Group — while `add`/`remove_group_member` take `private.require_group_work_manager`, because Appointment is a Group Responsible's Entry path (ADR-0009) and appointing a position is not. A Group Manager or Responsible is never removed by a roster call (`PT409 group_member_holds_role`, which replaces the legacy `project_members_protect_leader` trigger); eligibility and Minimum Level bind a write that **places** a Member (`PT400 group_member_not_eligible` / `group_member_below_min_level`), never one that demotes or removes, or an inactive Group Manager would be unremovable in both directions at once. On an Automatic-Membership Group, demoting to `member` deletes the row and asking for one where none exists is `PT409 automatic_group_has_no_roster_members`. Lock order is **gate → `groups` FOR NO KEY UPDATE → the roster row FOR UPDATE**: taking the Group first would invert `update_group`'s order, which holds a Manager's roster row `for share` and then reaches for the Group.

**A command's gates and its effect are separable, and sometimes must be (#582).** `private.cancel_event_effect(p_event_id, p_reason, p_actor)` is the write-and-fan-out of an Event cancellation with no authority check of its own; `private.cancel_event_impl` keeps every gate and calls it, and `private.archive_group_impl` calls it directly. The reason is not tidiness: `cancel_event_impl` decides authority per Event **from the actor**, which includes whether the actor can see the Event at all, so reusing it inside the archive cascade would answer a level-1 Group Manager `PT404 event_not_found` for an Event a BC had raised to Minimum Level 6 — aborting the whole archive with a reason naming neither the Group nor the cause. The authority for those cancellations is the **Group**, which the archiver already passed `require_group_manager` on. When a second command needs an existing command's effect under a different authority, extract the effect, leave the gates where they are, and grant the helper to nobody — never widen or re-run the original command's gate.

`groups_parent_name_uidx` remains partial (native Groups only); Wave 3 deduplicates legacy names before making it total. `private.cascade_group_path` updates descendants from a single path change and does not support a multi-row re-parent — it is a tripwire now, not machinery, since no function re-parents a Group at all.
